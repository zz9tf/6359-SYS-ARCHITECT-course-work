\section{Introduction}
\label{sec:intro}

Large language models (LLMs) need a lot of GPU memory. The 16-bit weights of a 7B-parameter model
take 15\,GB, and the key--value (KV) cache of every running request comes on top. To generate each
token, the GPU reads all the weights from memory, so generation is often limited by memory bandwidth
rather than by arithmetic~\cite{pope2023efficiently,gholami2024memorywall}. Quantization stores the
weights, and sometimes the activations, in 8 or 4 bits. Formats are named by what they quantize and
to how many bits (W4A16 means 4-bit weights and 16-bit activations), which suggests a simple rule:
fewer bits mean less memory, faster generation and a small loss in quality.

This rule can fail at each of its three steps. \emph{Memory:} the embedding, the output layer, the
KV cache and the activations stay in 16 bits, so the saving is smaller than the bit-width suggests.
\emph{Speed:} most formats must convert the weights back to 16 bits (dequantize them) before each
matrix multiply. This is free only if a fast kernel hides it while the GPU waits for memory, and
large batches make the GPU wait for arithmetic instead. \emph{Quality:} the rounding error depends on
the method and on the model.

Method papers report accuracy and kernel speed separately, usually on data-center
GPUs~\cite{frantar2023gptq,lin2024awq,frantar2025marlin,lin2025qserve}; comparison studies focus on
accuracy~\cite{jin2024comprehensive,li2024evaluating} or on one serving stack~\cite{kurtic2024give}.
But a user with one consumer GPU also picks a library, and the same format runs on very different
kernels in Hugging Face Transformers (bitsandbytes) and in vLLM (Marlin, CUTLASS).

We measure the whole trade-off on an NVIDIA RTX 5090, a 32\,GB consumer GPU, and answer the four
questions of our proposal. \textbf{Q1:} How much memory does quantization really save?
\textbf{Q2:} How do the time to first token (TTFT), the time per output token (TPOT) and the
throughput change? \textbf{Q3:} At which batch sizes and prompt lengths does a low-bit format become
faster, or slower, than BF16? \textbf{Q4:} How much quality does it cost? We test six quantized
configurations and BF16 on two stacks and five models (Qwen2.5 at 3B, 7B and 14B; Qwen3-8B and
Qwen3-32B to check generality). \Cref{fig:matrix} shows the effect of every configuration on every
metric. Its columns give our main findings, and each finding limits the next:

\begin{figure}[t]
\centering
\includegraphics[width=\linewidth]{impact_matrix}
\caption{\textbf{What each quantization configuration does to each metric} (Qwen2.5-7B). Rows group
the configurations by what they quantize; each cell compares one with BF16 on the same stack. Memory
and speed are ratios ($>1$: better); quality cells are coloured only if significant (\cref{sec:method}).
The two W8A8 rows differ because of their kernels (\cref{sec:mechanism}).}
\label{fig:matrix}
\end{figure}

\begin{enumerate}
\item \textbf{Memory (Q1, \cref{sec:q1}).} 4-bit weights shrink Qwen2.5-7B by only
  \WtNFSeven--\WtAWQSeven, not $4\times$, and less at run time; the saving pays off as capacity.
\item \textbf{Speed (Q2, \cref{sec:q2}).} The saved bytes become speed only with a fused kernel: vLLM
  turns \IdealAWQ--\IdealGQE\% of them into speed at batch size~1, bitsandbytes \IdealNF\% or less.
\item \textbf{Crossover (Q3, \cref{sec:q3,sec:mechanism}).} The gain lasts only while decoding is
  memory-bound, so batching ends it ($B\approx\AWQcross$); only FP8, whose fused kernel also
  multiplies in 8 bits, stays.
\item \textbf{Quality (Q4, \cref{sec:q4,sec:general}).} The cost is small at 8 bits and
  \MFourAbsMin--\MFourAbsMax{} MMLU points at 4 bits, less than the gain from a larger model.
\end{enumerate}
