\section{Background and related work}
\label{sec:background}

\textbf{Prefill and decode.} An LLM serves a request in two phases. \emph{Prefill} processes all $L$
prompt tokens at once, so for a batch of $B$ requests each linear layer multiplies its weights by
$M=B\cdot L$ rows; prefill sets the TTFT. \emph{Decode} then generates one token per request per step,
so each layer sees only $M=B$ rows; one step takes one TPOT. The keys and values of earlier tokens
are kept in the KV cache.

\textbf{A roofline view.} The roofline model~\cite{williams2009roofline} tells which resource limits a
kernel. For a linear layer $y=xW^\top$ with $x\in\mathbb{R}^{M\times K}$, $W\in\mathbb{R}^{N\times K}$
and $b$ bytes per weight, the arithmetic intensity (operations per byte moved) is
\begin{equation}
  I(M) \;=\; \frac{2MNK}{b\,NK + 2MK + 2MN} \;\approx\; \frac{2M}{b} \qquad (M \ll N, K).
  \label{eq:intensity}
\end{equation}
The kernel is memory-bound when $I(M)$ is below the ridge point $R$ (peak FLOP/s divided by memory
bandwidth) and compute-bound above it. On our GPU, $R\approx\RidgeBF$ FLOP/byte for BF16.
\Cref{eq:intensity} gives three predictions, which we test in \cref{sec:results}:
\begin{itemize}
\item[\textbf{P1}] Small-batch decode is memory-bound, so fewer weight bytes should give a
  proportional speedup, if the kernel hides the dequantization.
\item[\textbf{P2}] Weight-only formats (W8A16, W4A16) still compute in BF16: their speedup shrinks
  once they reach the compute roof ($M\approx bR/2$) and is gone once BF16 is compute-bound too
  ($M\gtrsim R$). W8A8 formats use 8-bit tensor cores, at least twice as fast, so they stay faster.
\item[\textbf{P3}] Prefill is compute-bound, so only W8A8 formats can shorten the TTFT.
\end{itemize}
The roofline leaves out the CPU time needed to launch each kernel. If this time exceeds the GPU time,
the step is \emph{host-bound}, and no saving of bytes helps.

\textbf{Formats.} LLM.int8()~\cite{dettmers2022llmint8} (INT8 weights and activations, with large
activation columns kept in FP16) and NF4~\cite{dettmers2023qlora} (4-bit NormalFloat weights) come
from bitsandbytes and run in Hugging Face Transformers~\cite{hfbnb}. GPTQ~\cite{frantar2023gptq} and
AWQ~\cite{lin2024awq} choose the rounding with second-order or activation information and store INT4
or INT8 weights; vLLM~\cite{kwon2023vllm} runs them with Marlin kernels~\cite{frantar2025marlin}.
FP8~\cite{micikevicius2022fp8} stores weights and activations in an 8-bit float that recent GPUs
support in hardware: the floating-point form of W8A8, which SmoothQuant~\cite{xiao2023smoothquant}
enables for INT8.

\textbf{Related work.} QServe~\cite{lin2025qserve} notes that W4A16 kernels lose their advantage in
large-batch serving; other work quantizes activations to 4 bits~\cite{ashkboos2024quarot} or
compresses the KV cache~\cite{liu2024kivi,hooper2024kvquant}. Dettmers and
Zettlemoyer~\cite{dettmers2023case} show that 4-bit models give the best accuracy for a fixed number
of model bits. Jin et al.~\cite{jin2024comprehensive} and Li et al.~\cite{li2024evaluating} compare
methods on accuracy, and Jin et al.\ note that quantization can slow inference down. Closest to us,
Kurtic et al.~\cite{kurtic2024give} find on data-center GPUs that W4A16 suits latency-bound use and
W8A8 suits high-throughput serving. We confirm this on a consumer GPU and add the Hugging Face path,
memory at run time, and a kernel-level explanation of every crossover.
