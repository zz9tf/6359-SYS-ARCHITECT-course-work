\section{Results}
\label{sec:results}

We explain \cref{fig:matrix} in the order its effects build on each other: saved bytes
(\cref{sec:q1}), speed at small batches (\cref{sec:q2}), how long it lasts (\cref{sec:q3,sec:mechanism}),
real traffic (\cref{sec:real}), quality (\cref{sec:q4}) and generality (\cref{sec:general}).

\subsection{Q1: How much memory does quantization actually save?}
\label{sec:q1}

\begin{figure}[t]
\centering
\includegraphics[width=\linewidth]{q1_memory_main}
\caption{\textbf{Q1: the saving is smaller than the bit-width suggests.} (a)~Weight-memory saving of
each configuration on Qwen2.5-7B against the nominal ratio of its bit-width (dashed). (b)~Saving of
the peak memory on HF as more tokens are in flight; dashed lines give the saving of the weights
alone.}
\label{fig:memory}
\end{figure}

\answer{Less than the bit-width suggests, and less again at run time. The saved memory pays off as
capacity.}

\textbf{Weights.} Quantization shrinks only the linear layers inside the decoder. The embedding and
the LM head, \EmbedShareSeven\% of Qwen2.5-7B's parameters, stay in 16 bits, and each format adds its
scales. So 4-bit weights save \WtNFSeven--\WtAWQSeven{} instead of $4\times$, and 8-bit weights
\WtIntEightSeven{} instead of $2\times$ (\cref{fig:memory}a). A model that counts these parts predicts
every measurement within \ModelErrMax\% (\cref{app:memory}).

\textbf{Run time.} At run time the saving shrinks further, because the KV cache and the activations
are not quantized at all. Their share grows with the number of tokens in flight. NF4's saving
therefore falls from \MemSmallNF{} for one short request to \MemBigNF{} for 32 requests of 2048
tokens, and LLM.int8(), which keeps extra copies of the activations, falls to \MemBigInt{}
(\cref{fig:memory}b).

\textbf{Capacity.} The saved memory is still valuable, but as capacity rather than as a smaller
footprint. vLLM turns it into KV cache, so AWQ-INT4 lets Qwen2.5-7B hold \KVratioAWQ{} as many tokens
as BF16 (\KVawqSeven{} vs.\ \KVbfSeven). \FourteenNote{}

\subsection{Q2: How do latency and throughput change?}
\label{sec:q2}

\begin{figure}[t]
\centering
\includegraphics[width=\linewidth]{speed_effects}
\caption{\textbf{Q2 and Q3: when the saved bytes become speed} (Qwen2.5-7B, speedup over BF16 on the
same stack). (a)~Decode speedup at batch size~1 against the weight memory saved: if decode time were
set only by the bytes read, every point would lie on the dashed line. (b)~Decode speedup as the batch
grows (512-token prompts). (c)~Prefill (TTFT) speedup for one prompt of growing length.}
\label{fig:speed}
\end{figure}

\answer{The saved bytes speed up decoding only when a fused kernel hides the dequantization. Prefill
gets faster only when the activations are quantized too.}

\textbf{Decode.} At batch size~1, decoding is memory-bound: vLLM's BF16 step takes
\TPOTbfVllmSeven\,ms, within \BWutilVllm\% of the time needed to read the weights once (prediction P1).
Fewer weight bytes should therefore shorten the step in proportion. On vLLM they do: AWQ-INT4 decodes
\AWQspeedup{} faster, GPTQ-INT8 \GPTQeightspeedup{} and FP8 \FPeightspeedup, which is
\IdealAWQ--\IdealGQE\% of their byte savings (\cref{fig:speed}a). On HF they do not: NF4 saves almost as
many bytes as AWQ-INT4 but is only \NFsevenB{} faster, and LLM.int8() is \INTeightslowdown{} slower.
The same bit-width can thus speed decoding up or slow it down. The difference lies in the whole stack
(method, activation path and engine), which \cref{sec:mechanism} takes apart.

\textbf{Prefill.} Prefill behaves differently, because it is compute-bound from the start (P3). Fewer
weight bytes therefore barely help: AWQ and GPTQ change the TTFT by at most \TTFTwoMax\%, and NF4 even
slows it by \TTFTnfSlow, since bitsandbytes dequantizes each matrix before using it
(\cref{fig:speed}c). Only the W8A8 formats, which also quantize the activations, shorten prefill: FP8
by \TTFTfpLong{} for a 2048-token prompt, and LLM.int8() by only \TTFTintLongOne, as its overheads eat most of the gain.

\subsection{Q3: When does lower precision pay off?}
\label{sec:q3}

\begin{figure}[t]
\centering
\includegraphics[width=\linewidth]{q3_speedup_heatmaps}
\caption{\textbf{Q3: where each configuration pays off.} End-to-end speedup of $B$ requests
($L$-token prompts, 128 generated tokens) over BF16 on the same stack, Qwen2.5-7B. Columns follow the
quantization type, rows the stack (no W8A16 runs on HF). Dashes: out of memory or not run. GPTQ-INT4
behaves like AWQ-INT4 (\cref{tab:crossover}).}
\label{fig:heatmaps}
\end{figure}

\answer{Weight-only gains last only while decoding is memory-bound. FP8 pays off at every batch size.}

The batch-1 gains rest on decoding being memory-bound, and batching removes that condition. Every
extra request reuses the same weights, so the work per byte grows with the batch (\cref{eq:intensity}).
The speedup of weight-only formats therefore shrinks as the batch grows (\cref{fig:speed}b) and is gone
near the BF16 ridge point (P2): AWQ-INT4 stops winning at $B\approx\AWQcross$ for 512-token prompts
(\cref{fig:heatmaps}). Long prompts add compute-bound prefill to each request, so the gain fades
sooner. Long answers add memory-bound decode and raise it (at $B=16$, \OutAWQSixteenShort{} for 32
output tokens, \OutAWQSixteenLong{} for 512; \cref{app:speed}). FP8 does not fade, because its kernel
also does the multiply in 8 bits, on tensor cores three times faster than BF16: it stays
\FPminEtoE--\FPmaxEtoE{} faster in every cell. LLM.int8() is W8A8 too, yet it is slower in every cell
(\INTminEtoE--\INTmaxEtoE), and NF4 wins only below $B\approx\NFcross$. The bitsandbytes formats never
reach the memory-bound gain in the first place; \cref{sec:mechanism} shows why.

\subsection{Why: kernels, the roofline and host overhead}
\label{sec:mechanism}

\begin{figure}[t]
\centering
\includegraphics[width=\linewidth]{q3_kernel_crossover}
\caption{\textbf{Why the crossover happens.} (a)~Speedup of each low-bit kernel over BF16 cuBLAS on the
matrix shapes of one Qwen2.5-7B decoder layer, against the tokens $M$ per multiply (the decode batch
size); ticks mark where it falls below 1.05. (b)~The same kernels on the measured roofline.}
\label{fig:kernels}
\end{figure}

\answer{The roofline explains the vLLM kernels. Extra kernels, and the CPU cost of launching them,
explain the HF stack.}

\textbf{Kernels.} To test the mechanism directly, we time each kernel alone on the matrix shapes of one
7B decoder layer (\cref{fig:kernels}a). Marlin W4A16 is \MarlinFourMone{} faster than BF16 at $M=1$,
as P1 predicts for four times fewer bytes. Its gain then shrinks and ends at $M\approx\MarlinFourCross$,
because it hits the same BF16 compute roof (\cref{fig:kernels}b). Real kernels reach that roof
gradually, so the crossover sits above the ridge point. FP8's compute roof is about three times higher
(\FPeightmeas{} vs.\ \BFmeas\,TFLOP/s), so FP8 is still \FPkernMmax{} faster at $M=8192$.

\textbf{Why the two W8A8 formats disagree.} The number format is not the cause: the GPU multiplies
INT8 as fast as FP8 (\INTeightmeas\,TOPS vs.\ \FPeightmeas\,TFLOP/s). LLM.int8() is slow because it
multiplies the outlier columns of the activations separately, in 16 bits. Each multiply thus needs
over a dozen small kernels, and the CPU waits for the GPU to find the outliers. Its layer runs at
\INTkernMone{} of the BF16 speed at $M=1$ and at most \INTkernMmax{} at large $M$; FP8, with two
kernels, is faster at every $M$ (\cref{fig:kernels}a).

\begin{figure}[t]
\centering
\includegraphics[width=\linewidth]{mech_decode_breakdown}
\caption{\textbf{Where an HF decode step goes} (Qwen2.5-7B, batch size~1, 512-token prompt): GPU time by
kernel type, and the time the GPU waits for the CPU (hatched).}
\label{fig:profile}
\end{figure}

\textbf{Host overhead.} The kernels explain the vLLM results, but not the HF ones. NF4's kernel alone
is \NFkernMone{} faster than BF16 at $M=1$, yet the whole NF4 model is only \NFsevenB{} faster, so
time must be lost outside the kernels. A profile of one decode step shows where (\cref{fig:profile}).
With BF16 the GPU is busy \BusyBFone\% of the step, with NF4 only \BusyNFone\%, and with LLM.int8(),
which launches \KernIntRatio{} as many kernels, only \BusyIntone\%. For the rest of the step the GPU
waits for Python to launch the next kernel. LLM.int8()'s INT8 multiplies do take half the time of
BF16's (\GemmIntone{} vs.\ \GemmBFone\,ms per step), but the kernels around them lose this gain. More layers mean more launches, so this overhead grows
with depth; this is why NF4 is slower than BF16 on the 36-layer 3B model. vLLM avoids most of it with
CUDA graphs, which replay a decode step with very few launches.
